# House additions (not from the book)

Rules with the `X` prefix were added from our own reviews to cover gaps the book does not address directly. They carry no chapter link. Cite them as `X<n>` and say "house rule" so readers know the source. Add new ones here when a review produces a real finding that no book rule covers; keep the same format.

- X1: A health endpoint reports readiness, not just liveness: it returns 503 when the service cannot serve its main operation (models not loaded, dependency down) and 200 only when it can, with a small JSON body stating what was checked. *Why:* load balancers and partners treat 200 as "will work"; a 200 from an empty service hides outages. *Check:* Does health return 503 when the primary operation would fail?
- X2: Retired routes and fields carry machine-readable deprecation metadata (`Deprecation` and `Sunset` headers or equivalent fields) with a date, and the replacement is named in the documentation. *Why:* clients and gateways can alert on them automatically; prose alone is missed. *Check:* Does every legacy route send a sunset date?
- X3: Errors produced by infrastructure in front of the API (413 body too large, 429 from a gateway, 504 from a proxy, 502) honour the API's documented error envelope and status semantics, or the limits are moved into the application. *Why:* a client's error handler parses one format; HTML from nginx breaks it. *Check:* Send an oversized body and a slow request; are the responses in the envelope?
- X4: Warnings returned alongside a success carry a machine-readable code and target, not only prose, and any silent transformation of the input (line breaks collapsed, markup stripped, values normalised) is either declared in the response or documented as a contract. *Why:* clients cannot branch on prose, and undeclared transformations are relied-upon behaviour (B26-5). *Check:* Can a client detect each warning kind without string matching?
- X5: For model-backed or algorithmic endpoints, the contract states whether identical input yields identical output within a major version, and how model or algorithm upgrades that change outputs are announced (version field, changelog, or header). *Why:* partners cache and test against outputs; silent drift breaks them. *Check:* Is output stability and its change policy written down?
- X6: Every success response has a declared content type and one shape per endpoint; no endpoint returns JSON for one input and plain text or a bare scalar for another. *Why:* extends P18-3 and H39-11 to content type. *Check:* Do all responses on a route share one `Content-Type` and one root shape?
- X7: A language parameter for messages (`Accept-Language`) is distinct from language fields that are part of the domain payload (source and target language of content). *Why:* D13-30 concerns the language of user-facing messages; content languages are business data. *Check:* Are message locale and content language separate inputs?
